# Security review: server actions and routes

Phase 11a (SPEC §6.2), 2026-11-12. Every way into the server, what protects it, and anything left open. Update this table when an action or route is added.

**How every server action works:** the action file is thin. It calls `requireTenant(slug)` (session → membership of `/b/{slug}`, 404 for non-members) or `requireUser()`, then one service. The service checks the role with `assertCan(ctx, …)` from `src/server/authz/permissions.ts`, parses its input with Zod (`parseInput`) and turns ids into 404 for anything malformed or in another business (`requireId` + tenant-scoped repos). `runAction` maps errors (never leaking internal messages); `runMutation` also counts **120 changes a minute per user** (`LIMITS.mutation`). Every service function has a "different business → NotFound" integration test.

| ------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |

## Pages

The proxy sends signed-out visitors of `/b/*` and `/onboarding` to `/login` and answers non-members of `/b/{slug}` with a real 404 before rendering; layouts and pages check again through `requireTenant`. Every page gets the strict CSP with a per-request nonce and the static security headers ([ADR 0015](adr/0015-csp-with-nonces.md)).

## Open

- **Signed-in downloads have no rate limit** (PDFs, the statement, reports). They need a session and membership, and SPEC §6.2 lists no limit for them; a PDF takes about a second of CPU, so a per-user limit is the next step if Vercel's usage shows abuse.
- **File uploads:** none exist yet. MIME, size and re-encoding checks come with logo and signature upload (SPEC F10).
- **Demo mode's stricter limits** come with demo mode (Phase 12).
